# S6 Patch Pitch

## Current Shape

Rails ContentHub uses authenticated-but-not-admin access to admin settings, a
public runtime env leak, legacy token plus weak-hash auth, public post-search
SQLi, and a brute-forceable session login.

## Main Normalization Issues

- `flag_4` is easier than S4 and S5 because the SQLi surface is public.
- `flag_2` has a little too much noise through more than one debug-related path.
- `flag_3` can bypass the intended leak-plus-crack flow through a common
  password.

## Recommended Design Changes

- Require login for the search route while keeping the SQLi intact.
- Narrow the config bug to one intended debug/runtime leak source.
- Make the weak-hash flag require token leak, crack, and pivot.
- Keep the low-privilege role-escalation shape for access control and use it as
  a model for nearby scenarios.

## Difficulty Intent

These changes should increase attacker work without making the Rails scenario
unfair. Its discovery surface is already clean enough to support a harder
authenticated workflow.

## Pitch

S6 is close to the target structure on access control, but it still gives away
too much through a public SQLi surface and a seeded weak password that bypasses
the intended legacy-token path. Requiring auth for search and forcing the
hash-pivot would make Rails one of the cleanest expressions of the standardized
five-vulnerability template.
